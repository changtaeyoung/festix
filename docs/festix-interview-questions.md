# Festix 예상 면접 질문 노트

> 오늘(8/19)까지 확정된 ERD·동시성 설계·인프라 결정을 기반으로 정리.
> 답은 전부 실제로 논의하며 도출한 내용이라 검증 가능함 — 자소서 원칙과 동일하게, 여기 없는 내용은 지어내지 말 것.

## 0. 오프닝 (프로젝트 한 문장 설명)

**Q. 이 프로젝트를 한 문장으로 설명해주세요.**
- 답 방향: "실사용자 없는 포트폴리오 프로젝트이며, 핵심 증명 포인트는 동시성 제어와 인프라 이해다. 실제 서비스 완성도(결제 UX, 부분 환불 등)보다 좌석 선점 동시성 문제를 어떻게 풀었는지에 집중했다."

## 1. 동시성 제어

**Q1. 왜 비관적 락(`SELECT FOR UPDATE`)을 선택했나요? 낙관적 락은 고려 안 했나요?**
- 티켓 오픈 순간처럼 경쟁이 극심한(hot spot) 상황에서는 낙관적 락 방식(버전 체크 후 재시도)이 오히려 재시도 폭주로 이어질 수 있음. 확정적으로 순서를 정하고 대기시키는 비관적 락이 이 시나리오엔 더 적합하다고 판단.
- (심화 대비) 낙관적 락과의 트레이드오프(처리량 vs 정합성 보장 방식)를 비교해서 설명할 수 있어야 함.

**Q2. 여러 좌석을 한 번에 예약할 때 데드락은 어떻게 방지했나요?**
- 좌석 ID 오름차순으로 정렬한 후 순차적으로 락을 획득. 모든 트랜잭션이 같은 순서로 락을 요청하게 만들어 순환 대기(circular wait) 조건 자체를 차단.
- 핵심: 이건 "누가 우선순위가 높은지"를 정하는 규칙이 아니라 "교착상태 자체가 발생할 수 없게 만드는" 규칙이라는 것.

**Q3. `WHERE status='AVAILABLE'` 같은 조건부 UPDATE는 왜 쓰나요? 락만으로는 안 되나요?**
- 이 한 줄로 "영향받은 row 수"를 통해 상호배제를 자동으로 얻을 수 있음 (1이면 성공, 0이면 이미 남이 가져감). 별도의 애플리케이션 레벨 우선순위 로직 없이, DB가 그 순간 원자적으로 판단해줌.
- 이 패턴을 좌석 선점뿐 아니라 TTL 만료 처리, 환불 처리에도 동일하게 재사용함 (일관된 동시성 제어 패턴).

**Q4. 좌석 하나만 실패해도 전체를 롤백하는 이유는요?**
- 예약을 "묶음 단위(reservation)"로 설계했기 때문에 all-or-nothing이 자연스러운 선택. 부분 성공을 허용하면 유저 입장에서 "내가 뭘 예약한 건지" 모호해지고, 나중에 환불 정책까지 이 원칙을 일관되게 유지함 (부분 환불 미지원과 같은 맥락).

## 2. 데이터 모델링

**Q5. `reservation`과 `reservation_item`을 왜 나눴나요?**
- 둘은 "단위(레벨)"가 다름. `reservation`은 "한 번의 예약 시도(묶음)", `reservation_item`은 "그 안의 개별 좌석". 온라인 쇼핑몰의 order/order_item 패턴과 동일한 구조.
- 처음엔 `booking`이라는 별도 이름을 시도했다가 `reservation`/`reservation_item`으로 통일 — 이름이 헷갈리면 설계 자체가 헷갈리기 쉽다는 것도 배운 지점.

**Q6. `user_id`를 `reservation_item`이 아니라 `reservation`에 둔 이유는?**
- "예약을 시도한 사람"은 좌석 하나하나가 아니라 그 시도(묶음) 전체에 대해 한 명. `reservation_item`에 두면 좌석 3개짜리 예약 하나에 동일 값이 3번 중복 저장되는 비정규화가 발생.

**Q7. `reservation_item.seat_id`에 유니크 제약을 안 건 이유는?**
- 같은 좌석이 시간이 지나며 여러 번 선점→만료→재선점될 수 있어, 같은 `seat_id`가 여러 row에 반복되는 게 정상. "지금 이 순간 좌석이 비어있는지"는 이 테이블이 아니라 `seat.status`(+ 비관적 락)가 전담. `reservation_item`은 히스토리 기록 역할.

**Q8. `user` 테이블명을 `users`로 바꾼 이유는?**
- PostgreSQL 예약어라서 매번 큰따옴표 처리가 필요해지는 걸 피하려고. 실수 유발 지점을 애초에 제거.

**Q9. 좌석/결제 상태를 네이티브 ENUM 타입이 아니라 VARCHAR + CHECK 제약으로 만든 이유는?**
- 네이티브 ENUM은 값 추가/변경 시 `ALTER TYPE`이 필요하고 트랜잭션 제약이 까다로움. 실제로 프로젝트 중간에 `REFUNDED` 상태를 추가해야 하는 상황이 생겼는데, VARCHAR + CHECK 구조 덕분에 CHECK 제약 문구만 수정하면 됐음 (실제 경험한 사례로 답변 가능).

## 3. TTL / 시간 관리

**Q10. 선점 만료 시각(`end_ttl`)을 조회 시점 계산이 아니라 INSERT 시점에 저장한 이유는?**
- 조회 시점마다 계산하면, TTL 정책이 5분→3분으로 바뀔 때 이미 진행 중인 예약까지 소급 적용돼버림. 이미 시작된 이벤트는 그 시점의 정책값으로 고정돼야 한다는 원칙.

**Q11. 반대로 결제 금액(`amount`)은 결제 확정 시점에 박제 저장했습니다. TTL과 반대 아닌가요?**
- 반대가 아니라 같은 원칙의 다른 적용. "이미 일어난 이벤트는 그 순간의 상태로 고정되어야 하고, 나중에 정책/가격이 바뀌어도 소급되면 안 된다"는 원칙은 동일함. TTL은 "선점 시작" 시점 기준, amount는 "결제 완료" 시점 기준이라는 차이만 있음.

**Q12. TTL을 PostgreSQL이 아니라 Redis로 관리하는 이유는?**
- PostgreSQL은 row 단위 TTL(자동 만료) 기능이 없음. Redis는 key expiration을 네이티브로 지원하고, keyspace notification으로 만료 이벤트를 구독할 수 있어 실시간 반응이 가능.

**Q13. Redis keyspace notification이 뭔가요?**
- Redis 기본 설정으론 꺼져 있는 기능(`notify-keyspace-events`)으로, key가 만료/삭제/변경될 때 이벤트를 pub/sub 채널로 발행하게 해줌. 이걸 켜야 "TTL 만료 → 자동으로 좌석 상태 되돌리기"가 가능해짐.

## 4. 장애 대응 / 안정성

**Q14. Redis pub/sub이 메시지를 놓치면 어떻게 되나요? 어떻게 대비했나요?**
- pub/sub은 발행 시점에 구독자가 살아있어야만 메시지를 받는 구조라, 서버 재배포 등으로 그 순간 죽어있으면 이벤트가 유실됨. 이를 대비해 별도의 안전망 배치(1분 주기 폴링)를 추가로 둠.

**Q15. 안전망 배치와 실시간 pub/sub을 같이 쓰는 이유는? 배치 하나로는 안 되나요?**
- 배치 폴링만 쓰면 주기 사이의 지연(최대 폴링 주기만큼)이 발생해 즉각성이 떨어짐. pub/sub만 쓰면 유실 리스크가 있음. 역할을 나눠서 pub/sub이 즉각 반응을 담당하고, 배치는 "놓친 것만 가끔 건져주는" 느슨한 보정 역할만 하도록 설계 — 그래서 폴링 주기도 촘촘할 필요 없이 1분 정도로 충분.
- 안전망 배치가 계속 유의미한 건수를 잡아낸다면, 그건 우연이 아니라 pub/sub이 구조적으로 새고 있다는 신호로 봐야 함 — 모니터링 지표로 추적.

**Q16. 결제 완료와 TTL 만료가 정확히 같은 시점에 겹치면 어떻게 되나요?**
- 좌석을 되돌리는 UPDATE에 `WHERE status='HELD'` 조건을 걸어둠. 결제가 먼저 완료돼 `status`가 이미 `SOLD`라면 이 조건에 안 걸려 영향받은 row가 0건 — 별도의 우선순위 로직 없이 조건부 UPDATE 하나로 안전하게 처리됨.

**Q17. 결제 대기 중에 TTL이 얼마 안 남으면 어떻게 하나요? 무한정 연장되지 않게는 어떻게 막았나요?**
- 결제 버튼 클릭 시점에 TTL을 1회 한정으로 5분 완전 리셋. `reservation.is_extended` 컬럼으로 중복 연장 방지.
- (심화) 30초 같은 짧은 연장이 아니라 완전 리셋을 택한 이유: PG사 응답 지연이 몇 초 안에 안 끝날 수도 있어, 너무 짧은 연장은 실질적인 보호가 안 됨.

**Q18. TTL 연장 시 Redis와 Postgres 중 뭘 먼저 갱신하나요? 이유는?**
- Redis 먼저, Postgres 나중. "좌석이 실제로 풀리는 기준"이 Redis이기 때문. Redis 갱신 성공 후 Postgres가 실패하면 화면 표시 오차 정도로 끝나지만, 반대 순서면 화면엔 "5분 남음"이라 뜨는데 실제로는 곧 풀려버리는 훨씬 위험한 불일치가 생김. (실패해도 덜 위험한 쪽을 먼저 실행)

## 5. 결제 / 환불

**Q19. 결제 시도 중 유저가 이탈해서 `PENDING` 상태로 영원히 남으면 어떻게 되나요?**
- 좌석 TTL 만료 처리(pub/sub 또는 안전망 배치)와 동시에 해당 `payment.status`도 `CANCELED`로 갱신. DELETE가 아니라 상태값으로 논리적 처리 — 이탈률 등 지표로 활용 가능하도록 기록 보존.

**Q20. `CANCELED`와 `REFUNDED`를 왜 구분했나요?**
- `CANCELED`는 결제 자체가 끝나지 않은 채 종료된 경우(TTL 만료, PG사 타임아웃), `REFUNDED`는 결제 완료 후 사용자 변심 등으로 환불된 경우. 발생 시점과 의미가 다른 이벤트를 같은 상태값에 욱여넣지 않기 위함. 실무에서 "이번 달 취소 건수"를 조회할 때 이 둘이 섞이면 지표 자체가 왜곡됨.

**Q21. 부분 환불(좌석 3개 중 2개만 환불)은 지원하나요?**
- 미지원, 의도적 스코프 제외. 좌석 선점 단계의 all-or-nothing 원칙을 예약 생애주기 전체(선점-결제-환불)에 일관되게 적용한 것. 부분 환불을 지원하려면 `reservation_item`에 개별 취소 여부, `payment`에 누적 환불액 컬럼이 추가로 필요한데, 이건 프로젝트 핵심 증명 포인트(동시성 제어)와 무관한 복잡도 증가라 판단해 제외.
- (심화 대비) 실무에서는 PG사의 부분 환불 API + item 단위 취소 추적으로 지원 가능하다는 것도 알고 있음을 언급 가능.

## 6. 인프라 / 기술 선택

**Q22. Kafka/RabbitMQ 같은 메시지 큐를 안 쓰고 Redis pub/sub을 택한 이유는?**
- 이 프로젝트 규모(단일 서버, 좌석 만료 이벤트 처리)에서는 Redis pub/sub으로 충분하다고 판단. Kafka/RabbitMQ는 오픈소스라 무료로 직접 호스팅 가능하지만(관리형 클라우드 서비스만 유료), 메시지 영속성·순서 보장이 필요한 수준의 복잡도는 아니라고 봐서 스코프에서 제외.
- (주의) "Kafka는 유료라서 안 썼다"는 답은 틀린 답 — 오픈소스임을 정확히 인지하고 답할 것.

**Q23. 금액 컬럼에 FLOAT이 아니라 DECIMAL을 쓴 이유는?**
- FLOAT/DOUBLE은 부동소수점 연산 특성상 금액 계산에 미세한 오차가 발생할 수 있음. DECIMAL은 고정소수점이라 금액처럼 정확도가 중요한 값에 적합.

## 8. ORM 선택: MyBatis → JPA 전환

**Q24. MyBatis로 시작했다가 JPA로 바꿨다고 들었습니다. 이유가 뭔가요?**
- 지원 목표 기업 중 JPA를 지향하는 곳이 있어 실무 감각을 다시 다지고 싶었고, ERD/DDL/동시성 전략이 이미 확정된 상태라 전환 비용이 거의 없는 시점이었음 (매퍼 XML이나 Repository 코드를 아직 작성하지 않은 단계).

**Q25. JPA로 바꾸면서 비관적 락 전략(오늘 설계한 동시성 제어)이 그대로 유지되나요?**
- `@Version` 기반 낙관적 락은 처음부터 검토 후 배제한 방향(경쟁 극심한 상황에서 재시도 폭주 우려)과 맞지 않아 사용하지 않음.
- 대신 `@Lock(LockModeType.PESSIMISTIC_WRITE)`로 `SELECT FOR UPDATE`를 그대로 재현.
- `WHERE status='HELD'` 같은 조건부 UPDATE는 엔티티를 조회 후 필드를 바꾸는 dirty checking 방식으론 조건절이 안 붙기 때문에, `@Modifying + @Query`로 직접 UPDATE 쿼리를 날리는 방식을 사용 — MyBatis 때와 동일하게 "영향받은 row 수"로 성공/실패 판단 가능.

**Q26. JPA로 전환하면서 새로 생기는 리스크는 없나요?**
- N+1 문제: MyBatis는 작성한 SQL 그대로 실행되지만, JPA는 지연 로딩된 연관관계를 순회할 때 반복 쿼리가 나갈 수 있음. `fetch join`이나 `@EntityGraph`로 대응 필요 — 실제 구현 단계에서 발생 여부 확인하고 대응할 예정.
